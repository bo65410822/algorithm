# 算法可视化架构

先阅读当前实现与 [references/architecture-contract.md](references/architecture-contract.md)，再提出或实施架构变更。

## 工作流

1. 识别变更属于算法过程、通用播放、视图渲染、教学解释还是页面外壳。
2. 保持单向数据流：`input -> run -> steps -> snapshots -> render`。
3. 从第二个算法模块开始抽取通用引擎，禁止继续向单个全局脚本追加算法分支。
4. 让算法模块只描述领域过程；让播放器只管理时间、游标和快照；让视图只渲染状态。
5. 保留当前可运行行为，采用小步迁移，不为尚未确定的 JVM、GC 或任意 Java 解析提前设计。
6. 在实现前明确新增或变更的契约、文件归属和兼容策略。

## 强制约束

- 用结构化步骤事件驱动 UI，禁止以 CSS 时间线或散落的 DOM 操作作为事实来源。
- 每一步必须可确定性重放、回退和重置，不依赖上一次动画结束后的 DOM 状态。
- 快照必须足以直接渲染，渲染函数不得偷偷执行算法。
- 模块标识、输入、代码行、步骤类型和统计字段必须稳定。
- 共享抽象只承载至少两个模块的真实共性；算法特有字段放在模块状态中。
- 当前产品是受限知识模块，不解析用户输入的任意 Java 源码。
- 架构变更必须附带至少一个现有冒泡排序回归检查。

## 输出要求

说明模块边界、数据流、契约变化、迁移顺序和验证方式。若实现代码，先完成最小共享内核，再接入现有冒泡排序，最后新增算法。
